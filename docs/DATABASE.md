# 数据库复用与必要性审计

## 结论

新安装只创建两张插件业务表。没有配置表、活动表、分享表、宣传图表、审计表或订单镜像表。

V10 数据库前缀由当前实例配置决定。下文省略常见的系统前缀，实际表名可能带有站点自己的前缀。

## 插件自有表

| 表 | 唯一职责 | 为什么不能复用官方表 |
| --- | --- | --- |
| `addon_community_group_buy_group` | 一次拼团的目标人数、已加入人数、模式、状态、时效和发团时风控快照 | 官方订单和优惠码表没有“多人共同成团”的聚合实体，成团前也没有订单可承载该状态 |
| `addon_community_group_buy_member` | 团与用户的唯一成员关系、加入顺序、权益状态和官方优惠码引用 | 官方优惠码使用记录只在下单后产生，无法表达成团前成员、团内唯一性和权益领取状态 |

两表通过唯一键和索引保证：

- 团号唯一。
- 同一发团请求不会重复创建团。
- 同一用户不能重复加入同一个团。
- 一个官方优惠码只能归属于一个团成员。
- 团状态、过期时间、成员状态和订单引用可高效查询。

## 复用的官方数据

| 官方数据 | 用途 | 插件不再复制的内容 |
| --- | --- | --- |
| `plugin.config` | 两套白名单、0.1 元开关、预算、次数与时效 | 不建配置表 |
| `product` 及商品价格数据 | 商品可见性、名称与基础售价 | 不建商品镜像表 |
| `addon_promo_code`、`addon_promo_code_product`、`addon_promo_code_log` | 权益码、适用商品和使用记录 | 成员表只保存官方优惠码 ID，不保存明文码副本 |
| `order`、`order_item` | 订单、商品、付款、退款与订单项 | 不复制付款时间、退款累计和订单项快照 |
| `host` | 首付与续费权威数据 | 不复制 Host，不修改续费价 |
| `system_log` | 业务与异常审计 | 不建独立审计表 |
| `plugin` | 当前插件 ID、版本和配置 | 分享链接不固化数字 ID |

## 安装、升级与卸载

- `install()` 使用 `CREATE TABLE IF NOT EXISTS`，不会先删除现有表。
- `upgrade()` 在修改表、列或索引前先探测状态，可重复执行。
- DDL 可能隐式提交，失败时保留现场并按迁移日志处理。
- `uninstall()` 默认保留两张表，因为其中包含经营、补贴和订单归因数据。
- 彻底删除数据属于站点运营方的数据保留决策，不由插件卸载自动执行。

## 发布检查

```bash
php tools/repository_audit.php
php tests/contract_test.php
```

审计脚本会断言新安装 DDL 恰好只有两条，并检查运行时没有重新依赖已退役的额外业务表。
